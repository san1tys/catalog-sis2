# Product Catalog — SIS #2

Простой Go-сервис для задания **Protocol implementation**: gRPC/protobuf поверх HTTP/2 и REST/JSON поверх HTTP/1.1 на одной бизнес-логике. Реализованы идемпотентное создание, таймауты, ограниченные повторы и воспроизводимое сравнение latency/payload.

```text
REST/JSON клиент ── HTTP/1.1 ──┐
                              ├── Service ── Memory store (mutex)
gRPC клиент ─────── HTTP/2 ────┘
```

## Выбор протокола и связь с SIS #1

В SIS #1 внешний API каталога описан через REST. Для SIS #2 это решение дополняется внутренним gRPC-каналом: `.proto` задаёт типизированный контракт, gRPC передаёт deadline, а protobuf позволяет сравнить компактность двоичного ответа с JSON. REST остаётся baseline. WebSocket не требуется для обычных запросов и ответов каталога.

Это дополнение к обоснованию протокола из SIS #1, а не утверждение, что gRPC уже был выбран в исходном документе. Проверка всей архитектуры и нагрузки SIS #1 в эту работу не входит.

## Запуск

Нужен **Go 1.24.7 или новее**. Для первой загрузки зависимостей нужен доступ к Go proxy. `go.mod`, `go.sum` и сгенерированный protobuf-код включены в проект; Docker и protoc для обычного запуска не нужны.

```sh
go mod download
make build
./bin/server
```

Сервер создаёт 2000 фиксированных товаров. Адреса по умолчанию доступны только локально:

- REST: `http://127.0.0.1:8080`
- gRPC: `127.0.0.1:50051`

Также можно выполнить `make run`. Другие параметры:

```sh
./bin/server -products 2000 -http-addr 127.0.0.1:8080 -grpc-addr 127.0.0.1:50051 -timeout 2s
```

Остановка — Ctrl+C. Все товары, изменения и ключи идемпотентности исчезают после остановки процесса.

## Контракт

| Операция | gRPC | REST |
|---|---|---|
| Карточка активного товара | `GetProduct` | `GET /v1/products/{id}` |
| Карточка любого статуса | `GetProductAdmin` | `GET /v1/admin/products/{id}` |
| Категории | `ListCategories` | `GET /v1/categories` |
| Поиск и листинг | `Search` | `GET /v1/search` |
| Создание | `CreateProduct` | `POST /v1/admin/products` |
| Изменение | `UpdateProduct` | `PATCH /v1/admin/products/{id}` |
| Скрытие | `HideProduct` | `DELETE /v1/admin/products/{id}` |

Поиск: `q`, `category`, `brand`, `price_min_minor`, `price_max_minor`, `sort`, `limit`, `cursor`. Размер страницы по умолчанию 24, максимум 48. Поддерживаются `price_asc`, `price_desc`, `newest`; текстовый поиск — простое вхождение в название. `relevance` в этом стенде означает порядок id без полноценного ранжирования. Подписанный курсор действует 60 секунд и привязан к фильтрам/сортировке; изменяющийся каталог не образует snapshot выдачи.

Цена — целое число в минимальных денежных единицах; валюта стенда — только **KZT**, например `price_minor: 12345` означает 123,45 KZT. Атрибуты — строки; пустой объект `attributes: {}` при PATCH удаляет все атрибуты, пропуск/`null` не меняет их.

Ошибки имеют одинаковые доменные коды у обоих транспортов:

| Код | REST | gRPC |
|---|---:|---|
| `INVALID_ARGUMENT` | 400 | InvalidArgument |
| `NOT_FOUND` | 404 | NotFound |
| `IDEMPOTENCY_KEY_REUSE` | 409 | AlreadyExists |
| `VERSION_CONFLICT` | 412 | FailedPrecondition |
| `RESOURCE_EXHAUSTED` | 429 | ResourceExhausted |
| `UNAVAILABLE` | 503 | Unavailable |
| `DEADLINE_EXCEEDED` | 504 | DeadlineExceeded |
| `CANCELED` | 499 | Canceled |

REST возвращает JSON `error.code`, `message`, `request_id`; gRPC — status и trailer `x-error-code`/`x-request-id` при ошибке.

## Идемпотентность и версии

Создание требует `Idempotency-Key` в REST или metadata `idempotency-key` в gRPC. Ключ привязан к актору (`X-Actor-Id` / `x-actor-id`; по умолчанию `anonymous`). Поле актора — область ключа, не механизм авторизации.

Под одним mutex хранилище проверяет ключ и hash нормализованного запроса, создаёт товар и сохраняет копию ответа. Поэтому конкурентный повтор не создаёт второй товар. То же тело возвращает сохранённый результат; другое тело с тем же actor/key — ошибку 409. Ключ действителен 24 часа в пределах жизни процесса. После истечения срока или перезапуска повтор может стать новой операцией.

При первом POST возвращается 201; при повторе — 200 и `Idempotency-Replayed: true`. PATCH требует `If-Match: "<version>"`, gRPC — `expected_version`. Устаревшая версия даёт конфликт. DELETE скрывает товар; повтор уже скрытого товара успешен.

```sh
curl -s http://127.0.0.1:8080/v1/products/1
curl -s 'http://127.0.0.1:8080/v1/search?category=2&sort=price_asc&limit=3'

# Выполнить дважды: 201, затем 200 + Idempotency-Replayed: true.
curl -i -X POST http://127.0.0.1:8080/v1/admin/products \
  -H 'Content-Type: application/json' -H 'X-Actor-Id: student' \
  -H 'Idempotency-Key: demo-create-1' -d @examples/create.json

# Тот же ключ с другим телом: 409 IDEMPOTENCY_KEY_REUSE.
curl -i -X POST http://127.0.0.1:8080/v1/admin/products \
  -H 'Content-Type: application/json' -H 'X-Actor-Id: student' \
  -H 'Idempotency-Key: demo-create-1' \
  -d '{"category_id":2,"brand_id":1,"title":"Different phone","price_minor":12345,"currency":"KZT","in_stock":true}'
```

Для ручной проверки gRPC можно отдельно установить grpcurl. Reflection включена:

```sh
grpcurl -plaintext 127.0.0.1:50051 list
grpcurl -plaintext -d '{"id":1}' 127.0.0.1:50051 catalog.v1.CatalogService/GetProduct
```

## Таймауты и повторы

Обёртка `client.Resilient` одинакова для обоих транспортов:

- чтение: timeout 80 мс, без автоматических повторов;
- Create и Hide: не более 3 попыток, до 1 секунды на попытку и до 5 секунд суммарно;
- между повторами — exponential backoff с full jitter, база 20 мс и потолок 200 мс;
- повторяются только временная недоступность, перегрузка и timeout отдельной попытки;
- PATCH автоматически не повторяется: после неизвестного исхода клиент читает административную карточку и проверяет версию.

При повторе Create используется тот же ключ и то же тело. Исчерпание timeout не доказывает, что запись не произошла.

Клиент передаёт остаток времени через gRPC deadline или REST-заголовок `X-Request-Deadline-Ms`. Сервер дополнительно ограничивает каждый вызов двумя секундами по умолчанию. Этот предел распространяется и на чтение HTTP-тела: неполная передача завершается с 504, а соединение закрывается. Для полностью прочитанных запросов дедлайн чтения сбрасывается, чтобы следующий запрос через keep-alive получил свой бюджет. Сервис и хранилище получают тот же контекст; фоновых запросов после отмены нет. Поиск проверяет отмену во время обхода и после сортировки; синхронная операция в памяти не прерывается посреди присваивания.

```sh
# Нулевой остаток времени: 504, работа с каталогом не начинается.
curl -i http://127.0.0.1:8080/v1/products/1 -H 'X-Request-Deadline-Ms: 0'
```

## Проверки

```sh
make vet
make test-race
```

Тесты поднимают временные REST/gRPC серверы на свободных локальных портах. Проверяются одинаковые ответы, replay и конфликт ключа, конкурентные дубликаты, версии, скрытие, пагинация и очистка атрибутов. Отдельно проверяются отмена работы хранилища, серверный потолок времени, ограничение повторов, повтор после потери ответа уже выполненной записи и отсутствие автоматического повтора PATCH. Инъекция отказов существует только в тестах.

## Измерения

При работающем сервере в другом терминале:

```sh
make bench
# Эквивалентная команда:
./bin/bench -warmup 100 -samples 1000 -repeats 3 -timeout 80ms -out bench/results
```

Benchmark читает карточку №1, страницу поиска из 24 товаров и категории. Каталог одинаков для обоих протоколов и во время сравнения не изменяется. На каждую операцию/протокол/повтор выполняются 100 прогревочных и 1000 измеряемых запросов. Порядок протоколов чередуется между повторами. Одновременно выполняется один запрос; соединения переиспользуются; retries и compression выключены.

Результат в `bench/results`:

- [REPORT.md](bench/results/REPORT.md): таблица фактических результатов и условия запуска;
- `raw.csv`: каждая измеренная попытка, latency, размер ответа и код ошибки;
- `summary.csv`: p50/p95/p99, успехи, ошибки и timeout для каждого повтора и общего набора;
- `environment.json`: Go, OS, архитектура, GOMAXPROCS и параметры команды.

Payload означает **размер тела ответа**, без HTTP-заголовков, фреймов gRPC/HTTP/2, TCP/IP и TLS. Для REST считается длина фактического JSON body, для gRPC — размер полученного protobuf-сообщения. Latency включает вызов, сериализацию и десериализацию. В gRPC также входит небольшой вызов `proto.Size` для учёта payload.

Ошибки и timeout входят в latency-квантили, а число успешных вызовов показывается отдельно. Квантили общего результата рассчитаны по всем попыткам, не усреднением p99 отдельных прогонов. При ошибках benchmark сохраняет результаты и завершает работу с ненулевым кодом. Повторный запуск заменяет файлы; для сохранения предыдущих результатов задайте другой `-out`.

Это **локальный последовательный microbenchmark**, а не нагрузочный тест. Он позволяет сравнить два конкретных клиента/сервера на одном стенде, но не доказывает 10 000 RPS, p99 <80 мс при пике или production capacity из SIS #1. Аппаратные характеристики, которые инструмент не измеряет, не подставляются в отчёт.

## Границы работы

Это учебный локальный стенд без авторизации и TLS. Административные маршруты не защищены; сервис не следует публиковать как рабочий каталог. Данные не переживают перезапуск. Поиск линейный с сортировкой в памяти, без Elasticsearch, фасетов и загрузки изображений.

Структура: `proto/` и `gen/` — контракт; `internal/domain`, `service`, `store/memory` — логика; `internal/transport` и `client` — протоколы и повторы; `cmd/server`, `cmd/bench` — запуск и измерения. Для регенерации контракта есть `make proto`; нужны отдельно установленные protoc, protoc-gen-go и protoc-gen-go-grpc.
